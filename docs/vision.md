# 项目构想与设计（v2）

> 一个能在 Mac 上直接启动的网页 Demo：你给一个数据分析目标，**数字分身（Twin）代替你**去驱动**真实的数据分析 Agent**——它真连数据源查真数、真跑分析；Twin 替你回答过程中的确认项、把关产出，最后把成果交付给你。全程你可随时进工作空间审阅完整对话与过程产物。

---

## 一、定位：一个「可运行切片」

北极星是：**人 + 数字分身（Twin）+ 工具 Agent 在同一块任务看板上协作的团队 AI 数据工作台**，核心链路是 **User → Twin → Agents**。

这个 Demo 不重做整个平台，而是把那条主链路里**最有说服力的一段**做成一个真实可跑的切片：

> **Twin 代替用户，驱动「数据分析 Agent」完成一次真实的取数 + 分析 + 交付，用户全程可旁观、可回溯、可随时接管。**

数据分析是旗舰垂类，我们就用它当演示垂类。默认演示模式返回示例数据，可接入真实数据源。

---

## 二、这次要「真实」的东西

| 能力 | 状态 | 说明 |
|---|---|---|
| **模型 API（LLM 网关）** | ✅ 跑通 | 任意 OpenAI 兼容端点（通过 `LLM_BASE_URL` 配置）；`POST /v1/chat/completions`，model 用 `{owner}/{id}` 或裸模型名。 |
| **数据查询** | ✅ 可用 | 默认 `sample` 演示模式返回示例数据；通过 `QUERY_BACKEND=command` 可接入真实数据源（需自行配置查询 CLI）。 |
| **数据分析 Agent 定义** | ✅ 现成 | `agents/data-analysis`：完整的身份 + 5 阶段 SOP + 8 分析范式 + 工具/技能清单。 |
| **NL→SQL 素材** | ✅ 现成 | `knowledge/` 下有各业务线的取数知识模板：主表、指标、维度、口径。请替换为你自己的真实业务知识。 |

**结论**：模型、取数、数据、Agent 人设、SQL 素材五件套齐全且验证可用。

> 安全底线：本机 key 只留服务端；数据查询工具**只允许 `SELECT`/`WITH...SELECT`**（禁 DDL/update/delete），从工具层面杜绝写操作，天然契合「只读演示」。

## 三、三方角色（对齐「统一 Agent」抽象）

设计哲学之一是 **Twin 与工具 Agent 是同一抽象的两种 `kind`**（统一运行时，不做第二套）。本 Demo 沿用：

| 角色 | kind | 定位 | 职责 | 边界 |
|---|---|---|---|---|
| **用户（你）** | — | 目标设定者 & 最终验收人 | 给目标、随时审阅、验收、拍板被升级上来的高风险决策 | 不盯每一步 |
| **Twin Agent（数字分身）** | twin（特权） | 用户的代理人 / 唯一编排者 | 理解意图、把任务派给数据 Agent、**替用户回答确认项、检查产出、必要时打回重做、决定何时上报**、最终打包交付 | 只提议不越权；高风险回来问用户 |
| **数据分析 Agent** | tool | 干活的专家（复用 `agents/data-analysis` 人设） | 走它的 5 阶段 SOP：命题澄清 → 任务拆解 → NL→SQL → **真实查数** → 分析 → 出结论；每到确认门就请示 | 不替用户/Twin 拍板；只读查询 |

**关键**：数据 Agent 面对的「甲方」是 Twin，不是用户本人。这正是 Demo 的看点。

---

## 四、核心机制（本项目的灵魂 · 与产品哲学逐条咬合）

### 4.1 Twin 唯一编排 + 代替用户验收

不是「用户问、Agent 答」，而是 **Twin 站在用户立场**驱动数据 Agent、逐步验收：结果口径对不对、有没有坑，不满意就打回重做。编排是**有界**的（防环、步数/预算上限），不引入两个 Agent 自由对话。

### 4.2 确认项：数据 Agent 的 SOP 确认门 → Twin 代答

**这是最巧妙的一处**：`data-analysis` agent 的 SOP 本就要求「每个阶段之间必须用户确认」——命题澄清、任务拆解、SQL 原文校对、关键数字校对……这些**确认门天然就是「确认项」**。

- **低风险确认**（用哪个口径、下钻哪个维度、SELECT 语句校对）→ **Twin 基于用户偏好直接代答**，任务不被打断。
- **高风险 / 拿不准**（超出用户目标范围、可能很贵的全量扫描、涉及写操作）→ Twin **升级回来问用户**，进「待确认队列」。

这与「Agent 只提议不越权、高风险走 HITL、人保留最终控制权」的哲学完全一致。Demo 的 wow 点就是：**大部分确认门 Twin 自动扛下来了，用户没被打扰，但每个代答都留痕可查。**

### 4.3 真实取数 — NL→SQL→数据查询→真实数据

数据 Agent 的查询是**真工具**：Node 后端通过数据查询适配器打到配置的数据源，跑真实 SELECT，拿真实结果。SQL 由 `knowledge/` 下的业务线模板生成（口径可信、字段合法）。

### 4.4 任务交付 + 「我替你做的决定」清单

完成后 Twin 打包交付：结论摘要（人话）+ 关键图表/数据 + **「我替你做的决定」清单**（把代答过的确认项和理由列出）+ 下一步建议。那份决定清单是建立信任的关键。

### 4.5 全程可回溯 + 文件优先

工作空间持久保留整个过程，且**以文件为真相源**：

```
tasks/{tid}/
  conversation.jsonl     # 用户⇄Twin、Twin⇄数据Agent 全部消息（含每个确认项如何被代答）
  sql/T{n}_*.sql         # 每条真实执行过的 SQL 原文
  data/T{n}_*.json       # 数据查询返回的真实结果
  decisions.jsonl        # 「我替你做的决定」清单
  STATE.md               # 任务状态/关键变量
```

用户随时进来都能看懂：谁说了什么、跑了哪条 SQL、拿到什么数、Twin 替自己做了哪些决定。

## 五、真实演示脚本（示例业务线）

1. **用户 → Twin**：「看看业务线A 最近一周核心指标有没有异常，帮我定位下，下班前给结论。」然后**走开**。
2. **Twin** 复述并锁定命题（对齐 SOP Phase 1），派给数据 Agent：「业务线A 近 7 天核心指标趋势 + 环比，异常则按维度A 下钻。」
3. **数据 Agent（确认门）**：「时间口径按自然日？主表用 `your_catalog.your_db.dm_table_a_di`、核心口径 `is_core_metric=1` 对吗？」
4. **Twin 代答**（不打扰用户）：「对；按自然日、该口径；日期分区用 `date` 整型过滤。」*(理由：用户一贯看自然日、认这张主表)*
5. **数据 Agent → 数据查询**（SELECT，真数据返回），给出趋势 + 环比。
6. **数据 Agent（确认门）**：环比 -9%，触发波动阈值(>8%)，「需要按维度A 下钻归因吗？」
7. **Twin**：「要，按 `dimension_a` 下钻 Top 变化。」→ 数据 Agent 再查一条真实 SQL。
8. **Twin 验收**：数据自洽、口径一致，通过。
9. **Twin → 用户（交付）**：「业务线A 近 7 天核心指标环比 -9%，主要拖累是维度A-1（-14%）。附：趋势图 + 我替你定的 3 个口径决定 + 建议下一步看版本关联。」
10. **用户**稍后回来看交付；**点开工作空间**能回看第 2–8 步全部对话、真实 SQL 与真实结果。

> 高光：3–8 步真实查了两次数据、Twin 代答了 3 个确认门，**全程没打扰用户**，但一切可回溯。

## 六、界面（状态优先）

界面以**状态**为主角，不是功能菜单：

```
┌────────────────────────────────────────────────────────────┐
│  任务：核心指标异动定位       [状态：待确认/执行中/已交付]    │
├─────────────────────────────┬──────────────────────────────┤
│  主对话区（用户 ⇄ Twin）     │  Agent 协作区（Twin ⇄ 数据Agent）│
│  - 目标                      │  - 数据Agent 三件套：状态+能力+在做啥│
│  - Twin 交付汇报             │  - ❓确认项 → ✅Twin 如何代答      │
│  - 「我替你做的决定」清单     │  - 🔧 真实查询调用 + 耗时          │
│  - ⬆️ 被升级的高风险待确认    │  - 🔁 打回重做记录                │
├─────────────────────────────┴──────────────────────────────┤
│  产物区：真实 SQL / 真实数据表 / 图表（保留历史版本，可回溯）  │
└────────────────────────────────────────────────────────────┘
```

- 任务状态 6 态（待办/执行中/待确认/已完成/报错/已暂停）。
- 产物 3 态（草稿/已确认/已发布）+ 渐进展开。
- 确认项、代答、真实工具调用、打回，都有醒目的可视化标记。

## 七、技术架构

```
浏览器（工作空间 UI，状态优先）
     │  SSE 流式：实时推 Twin / 数据Agent 的对话与工具调用
     ▼
本地 Node.js 服务（后端）
     ├── 编排引擎：驱动 Twin ⇄ 数据Agent 有界多轮（确认项代答 / 打回 / 升级 / 交付）
     ├── 两个 LLM 人设：Twin persona + data-analysis persona（都走 OpenAI 兼容 LLM 网关）
     ├── 真实工具：
     │     • data_query  → 数据查询适配器（只读 SELECT，默认演示模式，可接入真实数据源）
     │     • （可选）nl→sql 用 knowledge/ 里的业务线模板生成
     │     • （可选后期）Python 沙箱 / 更多数据源适配器
     ├── 模型代理：转发 LLM（key 只在服务端）
     └── 任务空间存储：tasks/{tid}/ 文件为真相源（conversation/sql/data/decisions）
     ▼
LLM 网关（OpenAI 兼容） + 数据查询适配器（默认演示模式，可接入真实数据源）
```

要点：
- **降级不阻塞**：数据查询未配置 → 演示模式返回示例数据，不崩；无模型 key → 提示配置。
- **只读安全**：查询白名单只放 `SELECT`/`WITH...SELECT`，拒 DDL/写。
- **前端**：原生 HTML/CSS/JS（零构建、`npm start` 即起）。
- **模型选型**：Twin 用响应快的模型（对话顺滑）；数据 Agent 用推理强的模型（分析准）。

# 05 · Twin 审查线

> 规则范围：DC-36 ~ DC-43 · 上级索引：[README](./README.md)
> 核心前提：**审查不是讨论。** 讨论可以发散后收敛，审查必须有终局——否则就变成完美主义死循环，交付永远差一口气。

## 一、DC-36｜同一交付物最多打回 2 次

第 3 次不许再打回，必须在三条路里选一条并留痕：

| 路径 | 做法 |
|---|---|
| **接受带缺陷交付** | 交付 + 在交付物中显式标注缺陷、影响范围与适用边界（对齐「边界与异常必写」） |
| **升级决策人** | 说明「两次打回未达标 + 缺口是什么 + 建议选项」，按 [DC-20](./02-推进与收束判定.md) 只问一个最小问题 |
| **换人换法** | 换 Agent、换方法或拆小任务重派，并说明原路径为什么走不通 |

**理由**：同一交付物两次打回未过，通常不是 Agent 不努力，而是**任务定义、口径或能力匹配有问题**。继续打回是在错误的层面上使劲。

## 二、DC-37｜打回三可原则

打回必须**可判定、可执行、可验收**，否则视为无效打回。

| 要素 | 要求 | 反例 |
|---|---|---|
| **可判定** | 指明违反了哪一条：引用 `acceptance_checklist.yaml` 的 `pc_*` 过关项或 `rt_*` 打回触发 id | 「感觉不太严谨」 |
| **可执行** | 说清补什么、按什么口径、查哪个维度 | 「再深入一点」 |
| **可验收** | 说清补到什么程度算过关 | 「补充完整」 |

**无效打回不计入 DC-36 的 2 次额度，但必须重写**——不能靠模糊打回无限续命。

合格示例：

> 打回（rt_no_drill）：发现消费时长 -9% 但未下钻归因。请按体裁、频道、新老用户三个维度下钻，定位贡献占比最高的维度；过关标准是能指出主因维度及其贡献占比，且各分项占比合计可解释。

## 三、DC-38｜一次申辩权

被打回的 Agent 有且仅有一次申辩机会。

| 环节 | 要求 |
|---|---|
| 申辩内容 | 必须带证据或规则依据。「我认为已经够了」不构成申辩 |
| Twin 必须回应 | **采纳**（撤销打回，并把该判据沉淀进 `LEARNINGS.md` 或验收清单）或 **驳回**（说明理由） |
| 申辩后仍不一致 | 按 [DC-16 分歧三分法](./02-推进与收束判定.md) 处置：`fact` 查数裁决 / `caliber` 查口径真相源 / `value` 升级决策人 |

**为什么要给申辩权**：验收方同时是编排方，天然强势。没有申辩通道，Agent 的正确异议会被结构性压掉——而这些异议往往正是最有价值的信息（它通常意味着任务定义或口径有问题）。

## 四、DC-39｜裁判与教练隔离：Twin 不下场辩专业结论

主持 / 验收角色与「专家意见」角色不可混。Twin 若有专业质疑，正确做法是**把它变成一个带判定标准的焦点，交给专家去判**，而不是自己下结论后要求别人认同。

| 情形 | 错误做法 | 正确做法 |
|---|---|---|
| Twin 觉得归因不对 | 「我认为主因是新用户占比，你改过来」 | 「焦点：新用户占比上升能否解释 ≥50% 的降幅？请用新老拆分数据判定」 |
| Twin 觉得方法有问题 | 「这个分析方法不行」 | 「按 rt_push_did，Push 类实验须用 DID。请说明为何直接对比 TGI」 |

## 五、DC-40｜验收依据必须外化

每次打回都要引用清单里的具体条目（`pc_*` / `rt_*`）。凭感觉打回不允许。

若某类硬伤在清单里没有对应条目：**先补清单**（走记忆晋升审批），**再用它打回**。顺序不能反（同 [DC-28](./03-收口与终止.md)）。

**为什么**：Twin 同时是规则制定者与执法者。若判据不外化，就无法区分「Agent 交付不合格」和「Twin 今天要求更高」——审查会变成不可复现的主观过程，Agent 也无法从中学习。

## 六、DC-41｜审查只管正确性与完整性

| 进审查线 | 不进审查线 |
|---|---|
| 是否正面回答了目标 | 文风、措辞 |
| 结论是否有数据支撑；推断是否标注 | 排版、表格样式 |
| 异动是否下钻到因 | 标题层级 |
| 口径是否全篇一致、是否与官方对齐 | 用词偏好 |
| 数值是否与已知水位量级一致 | — |
| 方法是否有红线硬伤（如 Push 未用 DID） | — |
| 边界与异常是否写明 | — |

排版问题走 `beautify`（样式 Agent），不与 `rework` 混用。

## 七、DC-42｜审查强度随信任等级变化，红线恒定

审查不是恒定强度，随 `server/domain/trust.js` 的 L1-L4 调整；**但红线项永不放松**。

| 信任等级 | 审查强度 | 打回额度 | 说明 |
|---|---|---|---|
| **L1 全程监工** | 逐条过全部 `pass_criteria` | 2 次 | 默认档 |
| **L2 审计模式** | 全量过红线项 + 抽查其余 | 2 次 | 低风险项事后抽查 |
| **L3 例外管理** | 只过红线项 + 异常信号（数值离水位、口径不一致） | 1 次 | 无异常直接放行 |
| **L4 全权委托** | 只过红线项 | 1 次 | 非红线缺陷改为「标注后交付」 |

**永不放松的红线项**（示例，真相源在 `business_context.yaml` 与项目踩坑表）：

- Push 类或存在组间干扰的实验必须用 DID，禁止直接对比 TGI。
- 口径必须与官方看板对齐；有差异必须量化并标注。
- 无数据支撑的因果结论必须标「推断」或降级为待验证方向。
- 关键指标数值明显偏离已知水位且无解释，必须存疑核对。

## 八、DC-43｜降级即回到 L1 强度

某类决策被连续纠正 3 次 → 该类型置 `escalate_only`，其审查强度回到 L1，不受当前等级影响（对齐 `trust.js` 的降级机制）。

信任是按类型累积的，也是按类型降级的。某一类判断不靠谱，不影响其他类型的放手程度。

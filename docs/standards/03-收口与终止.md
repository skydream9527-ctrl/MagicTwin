# 03 · 收口与终止

> 规则范围：DC-21 ~ DC-28 · 上级索引：[README](./README.md)

## 一、DC-21｜三种结束严格区分

| 语义 | 含义 | 有产出？ | 协议动作 |
|---|---|---|---|
| **收口 Close** | 正常结束，交付结论 | 是 | `close` / `deliver` |
| **叫停 Halt** | 终止某一条讨论线，场继续 | 局部 | `halt` + `redirect` |
| **终止 Abort** | 无产出结束 | 否 | `abort` |

**硬约束：不许用终止代替收口。** 只要有部分结论，就必须走收口并交付部分结论 + 说明缺口。把已投入的讨论直接扔掉，比结论不完美糟糕得多。

## 二、DC-22｜收口产出物规格

缺项即不合格。按 [DC-02 三分法](./00-总则与角色.md) 分层组织。

| 字段 | 内容 | 现有实现 |
|---|---|---|
| `verdict` | 一句话结论：方向 + 幅度，结论先行 | `close.verdict` |
| `facts[]` | 已定事实，每条带来源 / 口径 / [证据等级](./02-推进与收束判定.md) | 建议新增 |
| `judgements[]` | 判断，每条标注依据的事实 id；无数据支撑的标「推断」 | 建议新增 |
| `consensus[]` | 共识点 + 达到的共识级别（见 DC-23）；未明确对齐的不许写这里 | `close.consensus` |
| `disagreements[]` | 分歧登记表（DC-24 全字段） | `close.disagreements`（需扩字段） |
| `next_steps[]` | **最小闭环三要素：责任人 + 期限 + 完成标准**；未确认的用 `[待确认]` | `close.next_steps` |
| `restart_condition` | **重启条件**：什么条件满足后重议（见 [DC-35](./04-重启与重议.md)） | 建议新增 |
| `review_at` + `review_questions[]` | **回看时间 + 到期要检查的问题**（见 [DC-30](./04-重启与重议.md)） | 建议新增 |
| `decision_log[]` | 「我替你做的决定」：哪些是 Twin 代答、依据哪条规则 | `decisions.jsonl` |
| `refs[]` | 引用过的经验包 / 知识 / SQL / 数据指针 | `refs.jsonl` |
| `budget` | 用了几轮 / 几步 / 命中哪个收束触发器 | 建议新增 |
| `supersedes` | 若本次是重议，指向被替代的上一版结论 + 差异说明（见 [DC-33](./04-重启与重议.md)） | 建议新增 |

**边界与异常必写**：结论必须说明口径边界与异常处理（剔除了什么、极值怎么处理、适用范围到哪）。没有边界说明的结论，会在下一次被当成通用结论误用。

**只给一版结论**：收口不提供「方案 A/B/C 请你选」式的甩锅。需要人拍板的是决策项，走 `escalate` 并带选项（[DC-20](./02-推进与收束判定.md)）；已经能定的就定，别把选择成本推给决策人。

## 三、DC-23｜共识分级与定案门槛

| 级别 | 名称 | 含义 | 呈现 |
|---|---|---|---|
| **C0** | 无共识 | 连事实都没对齐 | 不允许进入 P4（强制收口时须显式标注） |
| **C1** | 事实共识 | 数据与口径一致，对「发生了什么」无争议 | `facts[]` |
| **C2** | 判断共识 | 对原因 / 结论方向与幅度看法一致 | `consensus[]` |
| **C3** | 行动共识 | 对下一步、责任人、完成标准一致 | `next_steps[]` |

**定案门槛 = C1 + C3，C2 非必须。** 允许「事实一致、判断有分歧、但下一步一致」——这在真实工作中极常见，也是最健康的收口形态。

> **要求先消灭判断分歧再行动，是把讨论拖成无终局的头号原因。** 判断本来就允许被新证据修正（[DC-02](./00-总则与角色.md)），所以正确做法是登记分歧 + 设回看时间，而不是辩到统一。

## 四、DC-24｜分歧登记表

分歧不许被抹平，必须结构化登记。缺项视为收口不合格。

```yaml
- id: DIS-1
  point: 消费时长下滑主因是体裁结构 还是 新用户占比上升
  positions:
    - by: data
      stance: 体裁结构主导（视频 -14%）
      evidence_level: A
    - by: ab-experiment
      stance: 新用户占比 +6pct 造成分母膨胀
      evidence_level: B
  kind: fact                # fact | caliber | value（见 DC-16）
  why_open: 缺新老用户 × 体裁的交叉数据，无法归因排他
  need_to_resolve: 补一次「新老用户 × 体裁」交叉查询（约 1 次取数）
  impact: 影响结论方向（是否要动内容分发策略）
  owner: <决策人 / 下一场>
  restart_condition: 交叉数据产出后自动重议（R2 级，见 04）
```

## 五、DC-25｜多数不能压倒证据与红线

共识不是投票。3 个 Agent 的一致意见不能推翻 1 份 A 级数据，也不能推翻业务红线（例：Push 类或存在组间干扰的实验必须用 DID，禁止直接对比 TGI）。

主持人有义务在收口时**显式指出「多数意见与数据 / 红线冲突」**，并按数据与红线定案。

## 六、DC-26｜叫停必须带 redirect

只叫停不给新方向，等于把场悬空，下一步必然空转。叫停后只能是三条路：换焦点 / 转动作（`ACT`）/ 收束。

## 七、DC-27｜终止五情形与终止记录

仅以下情形允许终止：

| 情形 | 说明 |
|---|---|
| 红线 | 命中硬护栏（G1-G5）且无合法降级路径 |
| 越权 | 需越过隔离边界读写才能继续 |
| 依赖缺失 | 关键依赖不可用（`*_NOT_CONFIGURED` / 取数不可达）且无替代 |
| 决策人撤回 | 决策人明确终止 |
| 前提失效 | 目标所依赖的前提被证伪，议题本身不再成立 |

**终止记录必须含三项**：终止原因 + 已获得的部分结论 + **恢复条件**（满足什么就能重开）。没有恢复条件的终止，等于把这段工作彻底作废。

## 八、DC-28｜收口暴露的机制缺口，24 小时内补规则

讨论过程本身会暴露流程缺陷：某类硬伤验收清单里没有、某个口径坑没登记、某类议题缺强制参会角色。这些必须在 24 小时内转成可执行的硬规则，否则同样的坑会再踩一次。

| 缺口类型 | 补到哪里 |
|---|---|
| 交付物硬伤类型未覆盖 | `knowledge/delivery/acceptance_checklist.yaml` 增 `pc_*` / `rt_*` |
| 代答边界判断失误 | `knowledge/rules/risk_matrix.yaml` |
| 业务口径坑 / 方法红线 | `knowledge/context/business_context.yaml` + 项目踩坑表 |
| 议题缺强制参会角色 | [DC-05](./00-总则与角色.md) 的强制参会表 |
| 讨论流程本身的漏洞 | 本目录对应规则 + [07 反模式](./07-参数与反模式.md) |

**顺序不能反**：先补规则，再用规则执法（见 [DC-40](./05-Twin审查线.md)）。凭临时判断打回或否决，无法被审计也无法沉淀。
